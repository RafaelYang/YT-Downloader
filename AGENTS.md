# Project learnings

- The active backend is `app.py`: FastAPI serves the plain frontend from `static/`, resolves a YouTube URL, and exposes separate SSE MP4, MP3, and Whisper jobs. Desktop mode is started by `desktop_app.py`, which imports the same app after setting per-run local credentials.
- Verified checks on 2026-08-31: `.venv/bin/python -m pytest -q` returned `41 passed`; `.venv/bin/python -m py_compile app.py desktop_app.py desktop_config.py desktop_platform.py whisper_model_manager.py` and `node --check static/app.js` succeeded. FastAPI TestClient emits one upstream deprecation warning about `httpx` versus `httpx2`.
- The stale moved project `.venv` was removed during the 2026-09-05 release cleanup. Recreate it with `python3 -m venv .venv`, install `requirements-dev.txt`, and continue using `.venv/bin/python -m ...` forms so generated console-script shebangs do not become a portability dependency.
- Runtime dependencies include `yt-dlp`, FFmpeg, PyTorch, OpenAI Whisper `small`, and `bgutil-ytdlp-pot-provider==1.3.2`; base requirements otherwise remain unpinned. Desktop/dev extras are pinned in `requirements-desktop.txt` and `requirements-dev.txt`.
- `start.bat` starts the loopback-only Windows desktop launcher from a prepared `.venv` and does not create a public tunnel.
- The transcript DOM mismatch was fixed by using `card-transcript` and `btn-transcript`; tests assert all three card/button ids. The Cookie UI/endpoints were removed, and local Cookie files are ignored and were deleted during cleanup.
- Desktop mode listens only on `127.0.0.1`, uses a random per-run token exchanged for an HttpOnly SameSite cookie, validates Host/Origin, accepts only explicit YouTube HTTPS hosts, and serves only output paths registered under a job. Writable data lives under `~/Library/Application Support/學人新創/YT Downloader/`; each resolved job lazily creates a shared `~/Downloads/<sanitized-title>_YYMMDD_HHMM/` folder for MP4, MP3, and transcript outputs, with `_2`, `_3`, and later suffixes allocated atomically on same-minute collisions.
- Completed MP4, MP3, and transcript cards expose a desktop-only `POST /api/open-folder/{job_id}/{kind}` action. It resolves only registered, still-existing output files and opens their parent through `desktop_platform.open_folder`; never accept a client-supplied filesystem path. Built-in-browser QA confirmed the button is hidden before completion, appears beside the save action, and reports success after Finder is invoked.
- User-facing output names are built by `output_stem()` and must keep the sanitized YouTube title first: `title_影片_<height>p.mp4`, `title_音檔.mp3`, `title_逐字稿_繁中.txt`, and `title_逐字稿_英文雙語.txt`. The registered disk path and `/api/file` Content-Disposition filename must stay identical.
- MP4 resolve results now expose descending exact-height choices with merged audio-size estimates and default to the highest available quality. The frontend uses the custom `quality-trigger` plus modal `quality-dialog`/`quality-options` component rather than a native `<select>`; each option is an accessible `role="option"` card with its estimate and selected state. The bottom `再下載一個` action was removed; the top URL field stays usable, and a completed MP4 is streamed from the registered local output through `/api/preview/{job_id}/mp4` into the page player without a cloud upload.
- QuickTime audio-only playback was reproduced with a valid AV1-video/AAC-audio MP4. Exact-height selection must prefer `avc1` video plus `mp4a` audio, but compatibility cannot rely on the selector alone: before publication, FFprobe must confirm H.264, AAC, and `yuv420p`/`yuvj420p` in an MP4 container. `ensure_playback_compatible()` atomically remuxes compatible streams or converts AV1/VP9/non-AAC media through bundled FFmpeg (`libx264`, AAC, `yuv420p`, faststart), then probes the result and rechecks the selected height. A synthetic AV1/Opus conversion, full decode, and packaged live YouTube H.264/AAC download passed on 2026-09-05.
- The packaged app previously ignored a valid legacy `~/.cache/whisper/small.pt` and its first transcription failed while Python `urllib` encountered a self-signed certificate chain. `whisper_model_manager.py` now verifies the publisher SHA-256, copies a valid legacy cache into App Support, or downloads through macOS system `curl` with TLS verification before an atomic install. A clean-data packaged run and a forced system-curl model download both passed; never work around this issue by disabling certificate checks.
- Multilingual transcripts in `0.1.3-dev` use Whisper `turbo`, native timestamp segments, and language-specific files: `_逐字稿_繁中.txt` or `_逐字稿_英文雙語.txt`. Traditional-Chinese mode applies OpenCC `s2twp`; English mode writes English first and a Traditional-Chinese translation second for every segment. Whisper aliases must cache by the publisher URL filename (`large-v3-turbo.pt`), not the API name (`turbo.pt`), or `whisper.load_model()` retries through Python `urllib` and can hit the known certificate-chain failure.
- Offline English-to-Chinese translation uses pinned `Helsinki-NLP/opus-mt-en-zh` revision `408d9bc410a388e1d9aef112a2daba955b945255`. `translation_model_manager.py` downloads the seven required files through verified HTTPS, checks a hard-coded SHA-256 manifest, and atomically installs the directory under App Support; never replace this with an unpinned runtime snapshot. The first English transcript downloads about 308 MB in addition to Whisper turbo's roughly 1.6 GB first-use model.
- PyInstaller with the current Torch build raises `NameError: name 'name' is not defined` from `torch._numpy._ufuncs` when Transformers imports the compressed module. Both platform specs must keep `module_collection_mode={"torch._numpy": "py"}`. The packaged `--ai-runtime-check` and optional `--translation-model-check` guard this: the final macOS `0.1.3-dev` App passed both, including an actual cached-model inference.
- Verified transcript checks on 2026-09-05: `54 passed`, Python compilation, and `node --check static/app.js`; synthetic English and Taiwan-Mandarin audio passed the full SSE job, timestamped output, language-specific filename, and desktop output folder flow. The final Apple Silicon ZIP is 394,897,651 bytes with SHA-256 `e62795f08ef4bf19aa394beb12fa220f8dd9f3af10a0afe587024a758778cdfd`; deep codesign and ZIP integrity passed. Windows Actions run `33962467334` passed the same 54 tests, packaged AI import check, local-health check, and silent install/start/legacy-autostart-cleanup/uninstall lifecycle; its 316,634,892-byte installer has SHA-256 `8d3dfcf47182707829219f2e65fb89a87ba2e656879c4e7e56f299549c2a6cf9`. A live public YouTube resolve was bot-blocked during this run, so this version still needs live packaged YouTube acceptance before calling the transcript flow fully verified.
- `desktop_app.py` provides a single-instance lock, menu-bar commands, authenticated reopen behavior, and clean PyInstaller multiprocessing startup. Starting with `0.1.1-dev`, the packaged app is manual-launch only: it never creates login-startup state, its menu has no autostart toggle, and each packaged launch removes the retired macOS LaunchAgent, Windows Run value, and `autostart.json` preference from older previews. macOS must still install an `NSApplication` delegate because Finder sends a reopen event to the existing LSUIElement process instead of starting a second process; the packaged LaunchServices test confirmed the same PID opened the page and the process count stayed at one.
- Jobs are still process-local and request-bound; SQLite queue/history, cancellation, automatic retry state, updater/rollback, and 24-hour temp cleanup remain unimplemented. Do not label the preview a complete v1.
- The current request-bound SSE design is not Cloud Run safe as a multi-instance service: job state is instance-local, `/tmp` is disposable in-memory storage, and download/transcription work remains tied to one request. For a small private deployment, a persistent VM plus authentication and durable job state is the lowest-change target. A multi-user deployment needs an external job store, queue/background worker, object storage, and expiring download URLs.
- The desktop-only product no longer ships the retired Docker, Cloud Run, Firebase Hosting, or temporary Cloudflare Tunnel deployment files. Keep cloud deployment out of the repository unless the user explicitly reopens that product scope.
- Live evidence from 2026-08-31: the existing `yt-downloader` Cloud Run service in `asia-east1` was Ready on revision `yt-downloader-00008-ld6` with 2 vCPU, 2 GiB, concurrency 4, and a 600-second request timeout. An in-app-browser resolve test of public short video `jNQXAC9IVRw` returned HTTP 400; Cloud Run logs showed all four yt-dlp strategies, including the bundled cookie strategy, failed with YouTube's "Sign in to confirm you're not a bot" response. Treat cloud YouTube extraction as unverified until it passes a live target-region acceptance test, and never infer download readiness from deployment health alone.
- Resolve strategy and download strategy are not equivalent: `android_vr` can advertise high formats whose URLs return HTTP 403, while a same-or-lower selector silently mislabeled a selected 720p job as 360p. The MP4 selector is now exact-height only, and FFprobe must confirm the completed height before publication; mismatches are deleted and reported instead of downgraded. The old yt-dlp test id `BaW_jenozKc` was unavailable and should not be used as the sole acceptance target.
- The Apple Silicon high-quality path uses pinned Node.js 24.20.0 arm64 plus bgutil-ytdlp-pot-provider 1.3.2. `scripts/fetch_macos_quality_runtime.sh` verifies both download hashes, builds an arm64 Canvas module, includes tagged GPL source, and applies `scripts/patches/bgutil-localhost.patch` so the child service listens only on a random `127.0.0.1` port. Provider stdout is discarded because it prints short-lived tokens. PyInstaller cannot discover the physical yt-dlp namespace plugin reliably; the frozen app loads only the base and HTTP provider source explicitly and marks the plugin pass complete to avoid duplicate registration.
- Apple Silicon media tools are FFmpeg/FFprobe 9.0.1 from Martin Riedl's build server, pinned and SHA-256 verified by `scripts/fetch_macos_tools.sh`; both are arm64 and only link macOS system frameworks/libraries. The build reports GPLv3+ configuration, so public releases need the required license texts and source-availability compliance.
- Verified Apple Silicon build command: `scripts/build_macos.sh`. The `0.1.1-dev` build produced `dist/YT Downloader by 學人新創.app` and `dist/YT-Downloader-0.1.1-dev-macOS-arm64.zip` at 307,641,726 bytes with SHA-256 `c4ff8f44d6ea22194eedf729d07344bd09fbced1d022c5b0935a84da2d99c6a7`; packaged health reported `0.1.1-dev`, a seeded legacy LaunchAgent and autostart preference were removed on launch, process shutdown left no bundled provider running, and codesign/archive integrity checks passed. The prior packaged app also passed clean-data MP4, MP3, Whisper-small MPS, same-process macOS reopen, open-output-folder, local MP4 preview, and 720p exact-height selection tests on the Apple M2 Pro; repeat live YouTube checks can still be blocked by the upstream bot challenge.
- The macOS preview is only ad-hoc signed: `spctl` rejects it, as expected. A public no-warning build still requires a publisher-owned Apple Developer ID, re-signing nested executables, notarization, and clean-Mac Gatekeeper/login-startup acceptance. Windows is also unsigned, and automatic updates remain unbuilt.
- Windows public distribution needs Authenticode, not Inno Setup's free `.issig` signatures. As verified against Microsoft's 2026-09-04 documentation, Artifact Signing Public Trust does not onboard Taiwan organizations or individuals, so recheck eligibility before choosing it; the practical GitHub-hosted-build path is a publicly trusted third-party CA with cloud/HSM signing. Sign the main app before packaging, let Inno Setup sign its uninstaller, sign the final installer, verify each signature, and generate release checksums only after signing. A self-signed certificate behaves like unsigned software in SmartScreen, and neither OV nor EV guarantees that a new release immediately avoids reputation warnings.
- Windows desktop mode is manual-launch only as of `0.1.1-dev` and removes the retired current-user `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` value left by older previews. It uses `os.startfile` for output folders, `node.exe` plus FFmpeg/FFprobe from bundled tools, and `CREATE_NO_WINDOW` for the local provider. App data stays under `%LOCALAPPDATA%\學人新創\YT Downloader\`; completed files stay under `%USERPROFILE%\Downloads\<title>_YYMMDD_HHMM\`. Installation does not require administrator privileges.
- Verified Windows x64 workflow: GitHub Actions run `33944432189` on `windows-2022` passed `45` tests, pinned-runtime verification, PyInstaller app startup/local-health checks, Traditional-Chinese Inno Setup construction, and the silent install/start/uninstall lifecycle. Keep `scripts/patches/bgutil-localhost.patch` LF-normalized through `.gitattributes`, or Windows `git apply` fails after checkout.
